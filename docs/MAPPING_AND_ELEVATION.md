# Mapping Regions & Elevation Architecture

This document provides extensive technical and architectural documentation regarding the Open-Yardage Architect's mapping regions, the collection and rendering of elevation data, and the handling of complex geometric topology (the "cookie-cutter" functionality). 

---

## 1. Mapping Regions

### Core Concept
Mapping regions (Terrain Overlays) represent the geometric footprint of different physical features on the golf course. These features serve as the primary spatial anchors for the architect tool, allowing users to define playable areas, hazards, and boundaries.

### Terrain Classifications
Regions are categorized by terrain type. Each classification dictates not only the visual styling on the map but also how the system calculates interactions (e.g., whether a contour line should be drawn within it). The current classifications include:
- **Playable Areas:** Green, Tee box, Fairway, Rough
- **Hazards & Boundaries:** Bunker, Water, Trees / OB, Cart path
- **Other:** Unassigned

### Interaction Phases
The frontend handles regions through specific interaction phases to provide visual feedback:
- **Drawing:** When a user is actively defining the polygon boundaries.
- **Idle:** The default state, rendering with a subtle opacity.
- **Hover & Selected:** The active states where the polygon opacity increases and a distinct border stroke is applied to indicate it is ready for modification.

### Data Architecture
When a user finishes drawing or editing a region, the data is pushed to the Supabase backend:
- **`terrain_overlays` Table:** Stores the core entity, including the terrain classification, the raw GeoJSON data, and a PostGIS geographic shape for spatial queries.
- **`terrain_overlay_holes` Table:** A many-to-many junction table that links the terrain overlay to a specific hole.

## 2. Elevation Gathering and Rendering

The Open-Yardage Architect provides a highly detailed topographic view of the course by gathering raw elevation data and dynamically rendering it as styled contour layers.

### Data Gathering (The Source)
Elevation data is primarily sourced from the **USGS EPQS (Elevation Point Query Service)**. 
- For specific point lookups (e.g., placing a pin or tee marker), the system queries the USGS API using the geographic coordinates (WGS84 / SRID 4326). 
- The USGS API natively returns elevation values in meters. The system immediately converts these values into yards (multiplying by ~1.09361) to maintain consistency with standard golf yardage metrics.

### Grid Generation
To render continuous topographic contour lines over an entire hole, a single point lookup is insufficient. 
- The system requests a dense bounding-box grid of elevation data at a 3-meter resolution.
- To maintain performance, this grid is generated by a dedicated Supabase Edge Function (`generate-elevation-grid`).
- The resulting matrix of elevation values is aggressively cached in the database (`hole_elevation_grids`) to prevent redundant external API calls and ensure rapid map loading times for subsequent visits.

### Topographic Rendering (The Engine)
The rendering of these elevation matrices into visual contour lines is handled purely on the client side using the React-Leaflet map canvas:
1. **Matrix Negation & Thresholding:** The grid values are loaded and negated. The system generates thresholds at 1.0-yard intervals spanning from the lowest to the highest elevation point on the hole.
2. **D3-Contour Generation:** The raw grid data is passed through the `d3-contour` library, which traces the matrix and generates raw GeoJSON MultiPolygons representing the elevation bands.
3. **Cookie-Cutter Masking (Turf.js):** Drawing contour lines across the entire bounding box would look messy and cover non-relevant areas (like houses or parking lots). The system uses `@turf/intersect` to clip the raw contour lines strictly against the *Playable Areas* (Greens, Fairways, Tees, Rough). The contours are essentially masked so they only appear where the game is played.
4. **Dynamic Shading:** To create a 3D depth effect, the contour layers are stacked. Lower elevations are assigned a slightly higher fill opacity of a dark slate color. Because they are stacked recursively, the lowest points on the hole accumulate the most layers, becoming visibly darker, naturally drawing the user's eye to depressions and drainage areas.

## 3. Complex Topology: The "Cookie-Cutter" Features

A critical requirement for accurate course mapping is the ability to represent complex shapes with interior boundaries—commonly referred to as "Donut Polygons". 

### The Concept
In course design, terrains often overlap entirely. The most common scenario is a Green completely surrounded by a Fairway. Instead of drawing a Fairway that awkwardly wraps around the Green, the architect uses a "Cookie-Cutter" tool (provided by Leaflet-Geoman) to punch a hole directly through the Fairway polygon, dropping the Green into the resulting void.

### Technical Representation
In standard GeoJSON and PostGIS, a simple polygon is represented by a single array of coordinates (the exterior ring). A "donut" polygon is represented by an array of arrays:
- **Index 0:** The exterior ring (the outer boundary).
- **Index 1 to N:** The interior rings (the holes cut out of the shape).

### Interaction Constraints & Known Pitfalls
Handling these complex topologies in the frontend requires specific care:
- **Coordinate Extraction:** When reading the shape data from the Leaflet canvas to push to the database, manual array parsing (e.g., extracting just the first coordinate array) is dangerous. It will successfully save the outer boundary but instantly destroy the interior hole. Native GeoJSON exporters (`layer.toGeoJSON().geometry`) must be strictly used to ensure the nested arrays representing the cookie-cutter holes are perfectly preserved in the database.
- **Event Management during Vertex Editing:** Editing these complex shapes exposes multiple vertices (both on the exterior and interior rings). Manipulating these vertices can cause event propagation collisions between the drag action and the underlying map canvas. Strict event isolation (preventing drag events from bubbling up to the map layer) and pausing React state updates during the physical drag motion are required to prevent the map from violently panning out from under the user's cursor.
